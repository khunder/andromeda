# Changelog

## 2026-07-19

- Closed the "known limitation" from the intermediate-catch-event work above: `/signal` previously 404'd outright if the paused process instance wasn't currently live in the resuming container process's memory (e.g. the container that paused it had since restarted), since `ContainerService.processInstances` is per-process and starts empty on every restart. Inspired by jsflow's `createInstance(id)` restore path (`restoreProcessInstanceFormPersistentStore`/`getProcessInstanceStatus`/`variables.restoreVariableValues`) — adapted, not ported, since Andromeda tracks two-phase "waiting" state via `FlowEvent` rather than jsflow's dedicated per-gateway status map. Added `{ProcessDef}ProcessInstanceService.restoreInstance(processInstanceId)` (service.njk): looks the instance up via a new `PersistenceGateway.getProcessInstance`/`ProcessInstanceRepository.getProcessInstance`, returns `null` if it doesn't exist or isn't Active (never resurrects a Completed/Aborted instance), otherwise reconstructs it via the constructor's already-existing (but previously never actually exercised) `processInstanceId` resume path, rehydrates its variables via a new `restoreVariableValues()` on the context class (process-instance-context.js.njk; reads every persisted `Variable` row for the instance via a new `PersistenceGateway.getVariables` wrapping the already-existing `VariableRepository.getVariables` and assigns each through the real setter — so it gets transcoded to its declared type exactly like any other assignment — then marks it clean immediately, since it's not a new change), and re-registers it in `ContainerService`'s registry. `controller.njk`'s `/signal` handler now falls back to `restoreInstance()` only when the in-memory lookup misses, so the already-fast common case (instance still live) is unaffected. Added `test/integration/intermediate-catch-event-restore-after-restart.int.test.js` (reuses the fixture from the test above): starts a process instance in one embedded container, lets it pause, stops that container entirely, starts a second, independent container process for the same deployment (sharing the same persisted database, empty in-memory registry), and signals the *second* container — verified via the containers' own logs that two genuinely different PIDs handled the pause and the resume, confirmed the pre-restart variable value survived the round trip, and confirmed the post-signal script task's update landed correctly on top of it.

- Implemented `bpmn:IntermediateCatchEvent` support (pause a process instance until an external signal resumes it), inspired by beeflow's design — though beeflow's own implementation turned out to be an unfinished prototype (the resume path was never actually wired: its generated `/signal` handler creates a brand-new process instance instead of resuming the paused one, and its `resumeExecution`/`executeBody` flags are read but never actually set anywhere), so only its `NodeContext` shape (`executeBody`/`alternateBody`, matching Andromeda's own already-dormant `build.method.njk` scaffolding almost field-for-field) carried over; the actual pause/resume wiring below is new. `CatchEventNodeProcessor` was previously unregistered dead code with the wrong BPMN type (`bpmn:CatchEvent`, an abstract meta-model type bpmn-moddle never actually parses an element as — real catch events parse as `bpmn:IntermediateCatchEvent`) — fixed the type, registered it in `bpmn.processor.js`, and extracts the signal name off `eventDefinitions[0].signalRef.name` when the diagram declares one (not required — a catch event with no event definition still pauses generically). Also fixed `isTwoPhaseComponent()` (service.njk) which checked for the same wrong `"CatchEvent"` string, so a real catch event's incoming flow was never actually being marked Active/pending as intended. On first arrival `flowModel` is the raw incoming-flow-id string used everywhere else in this codebase (see 2026-07-18's parallel-gateway/exclusive-gateway work), so `flowModel.executeBody` is always falsy and the node naturally falls into `alternateBody` (log "now waiting") without reaching its outgoing flows — no special-casing needed there. Added a generic `POST /signal` route (one handler for every catch event node in a workflow, not one route per node): looks the process instance up in `ContainerService`'s existing (already-built, just never used for this) in-memory instance registry, confirms via a new `PersistenceGateway.findActiveFlowEvent`/`FlowEventRepository.findActiveFlowEvent` that it's genuinely still paused at that node (not already resumed or never reached), applies any given `variables`, closes the pending flow event, and calls `fn_<nodeId>({executeBody: true, id: flowId})` directly — deliberately not through `callFunction`, since its `...Object.values(args)` spread only forwards a single positional value and can't carry an `{executeBody, id}` shape. Known limitation (documented in code, not silently swept under the rug): resume only works while the process instance is still live in that container process's memory — there's no rehydration of a paused instance's variables from persistence after a container restart; no code anywhere in the engine has that capability yet. Along the way, found and fixed a real, previously-invisible bug in `web.module.js`'s global Fastify error handler: it unconditionally replied with a bare `500` and an empty body for every thrown error, discarding whatever `.statusCode`/`.message` the route handler had actually set — harmless for `/start` (which never needed to distinguish error cases in its response), but it broke `/signal`'s very reason for setting 400/404/409 (so a caller can tell "you sent garbage" from "already resumed" from "server broke") outright, silently downgrading all of them to opaque 500s. Fixed to respect a valid `error.statusCode` and return `{message}` in the body. Added `test/integration/intermediate-catch-event-signal.int.test.js` + `test/resources/intermediate-catch-event-signal.bpmn` (Start → script task → catch event waiting on signal "approval" → script task → End): verifies the instance genuinely pauses (Active process instance, catch event's outgoing flow never fires, downstream variable still holds its pre-pause value) before signaling, that signaling resumes it to completion with the downstream variable correctly updated, and that a second signal to the same already-resumed node is rejected with 409 rather than silently re-running it.

- Fixed a real crash reported from a live diagram: `VariableEncoder.transcodeVariable`'s `boolean` case only special-cased `value === undefined`, not `value === null` , but `Variable`'s private `#currentValue` field defaults to `null`, not `undefined`. Worker-executed script tasks' `applySnapshot()` re-applies *every* declared variable through its setter after each script task runs, not just the ones that script touched, so any script task that left a declared boolean variable untouched hit this: `this[name] = snapshot[name]` → the setter → `transcodeVariable(null, "boolean", ...)` → thrown `cannot transcode variable X of type boolean, possible values [true|false|""]`, crashing the node's method entirely (matches the reported stack trace, which crashed inside `fn_SetAge`, a script task that only ever touched a different variable). Fixed by treating `null` the same as `undefined` at the top of `transcodeVariable` , pass through unchanged rather than attempting type coercion, for every type, not just boolean (other types didn't throw on `null` but silently produced wrong values, e.g. `string` would stringify it to the literal text `"null"`). Added a `null` case to the existing `transcode-variable-encoder.ava.test.js` boolean suite, plus a new integration-level regression test (`test/integration/transcode-variables-worker.int.test.js` + `test/resources/untouched-boolean-variable.bpmn`) exercising the actual runtime path this bug lives in (worker thread → `applySnapshot` → transcode), not just the unit-level function call: a script task sets `age` only, leaving a declared `isAdult` boolean untouched (must not crash), then a second script task sets `isAdult` from `age` (must correctly transcode `true` through the same worker round trip). Verified the regression test actually catches the bug: reverted the fix and confirmed the test fails (process instance never completes, crashing in `fn_SetAge` exactly as reported) before restoring it.
- Implemented conditional sequence flow and real exclusive (XOR) gateway branching, inspired by andromeda's design: its `ExclusiveGatewayProcessor` is a thin pass-through that doesn't touch conditions at all , the shared next-node dispatch logic evaluates each outgoing flow's own `conditionExpression` independently and only takes flows that evaluate truthy, off of ANY node type, not just gateways. Andromeda already computed this per-flow `executable` flag (`build.method.next.calls.njk`) but never actually gated the call on it , every outgoing flow fired unconditionally regardless. Fixed by merging the two previously-separate loops (the flag was computed in one block-scoped loop and read in a different one, so it was never actually visible where it was needed) into one: each outgoing flow's condition (if any) is evaluated via `this.evaluate(...)`, using `stringify()` instead of raw string interpolation to safely embed the condition body (the old `'{{ ... }}'` form would have broken on a condition containing a quote), and `callFunction` only fires when it's truthy. Flows with no condition are always taken, so parallel-gateway forks and any node with unconditioned outgoing flows are unaffected. `ExclusiveGatewayNodeProcessor` stays an intentional pass-through stub, matching andromeda , no dedicated per-flow-type logic needed since the generic mechanism already handles it. Also fixed a bug this exposed: `PersistenceGateway.createFlowEvent(...)` fired for every outgoing flow unconditionally, before the executable check , harmless while every flow always fired, but now it would record a misleading "flow was taken" event for a flow whose condition was false; moved inside the `if (flowExecutable)` block so a flow event is only recorded for a flow actually traversed. Matching andromeda, this does NOT implement first-match/mutually-exclusive branch selection (if two outgoing flows' conditions are both true, both fire , the diagram author is relied on to write actually-exclusive conditions) or the `default` sequence flow attribute (andromeda doesn't read it either). Added `test/integration/exclusive-gateway-conditional-flow.int.test.js` + `test/resources/exclusive-gateway-conditional-flow.bpmn` (a script task sets `age = 20`, then an exclusive gateway with two conditioned flows `age >= 18`/`age < 18`): verifies the adult branch's flow event fires exactly once and the minor branch's never fires at all. Debugging note: the fixture's first draft omitted the `<bpmn:property>`/`<bpmn:itemDefinition>` declaration for `age` , without it the generated context class has no getter/setter for the variable, so the worker-thread script's assignment never round-trips back via `applySnapshot` (which only copies declared variables), silently leaving `age` `undefined` for every downstream read; not an engine bug, just a fixture omission, fixed by declaring the property (as the other variable-using fixtures already did).
- Fixed `test/resources/parallel-gateway-join.bpmn` not rendering any sequence-flow lines in the designer: its `<bpmndi:BPMNPlane>` had `BPMNShape` DI entries for every node but no `BPMNEdge` entries for any of its six `sequenceFlow`s. DI-only change , verified 0 bpmn-moddle parse warnings and the integration test that compiles this fixture still passes.

## 2026-07-17

- Added event replay and snapshots to the persistence module, making the event store a real source of truth: a new `ReplayService` rebuilds a stream's read model by restoring its latest snapshot (or resetting when none exists) and re-dispatching only the events logged after it, without re-persisting them. Snapshots are read-model state dumps stored in a new `Snapshot` collection keyed by `(streamId, streamPosition)`, written automatically every 100 events (after the event is safely in the log) or on demand. Everything is exposed through `PersistenceGateway.replayStream/replayAll/snapshotStream`, keeping the gateway the persistence layer's only external entry point.
- Engine restarts no longer corrupt event numbering: `PersistenceGateway.init()` now seeds each stream's in-memory position counter from the highest persisted position in the log, instead of restarting at 0 and colliding with the unique `(streamId, streamPosition)` index.
- Fixed status-transition writes (`complete`/`removeLock` on process instances, `close`/`abort`/`fail` on flow events) creating partial, unvalidated documents when the target record didn't exist , they now use a non-upserting update.
- Fixed event `streamPosition` handling: emitted events no longer hardcode position 0 (the stream assigns it), and a legitimate position 0 supplied by a caller is no longer silently overwritten.
- Event timestamps are now ISO-8601 (`toISOString`) instead of locale strings, so they sort correctly and keep millisecond precision.
- Fixed Mongoose `_id` defaults on the process-instance and flow-event models generating the same UUID for every document (`default: v4()` was evaluated once at schema definition).
- Performance: Ajv event and payload schemas are now compiled once and cached instead of recompiled on every event.
- Replaced deprecated Mongoose calls in the base repository (`count`→`countDocuments`, `remove`→`deleteOne`/`deleteMany`), unblocking future Mongoose upgrades.
- Fixed the unit-test fake repository matching a nonexistent `id` field (documents are stored under `_id`) and its `findOne` throwing instead of searching.
