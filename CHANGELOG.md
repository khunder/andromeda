# Changelog

## 2026-07-18

- Fixed `process-instance.int.test.js`: tests were calling `EventStore.apply` without the streams ever being registered/initialized, causing the "cannot find an aggregator for the streamId" failures. Added `beforeAll`/`afterAll` hooks around `PersistenceModule.init()`/`dispose()`, and switched the hardcoded `"PROCESS_INSTANCE"`/`"CREATE_PROCESS_INSTANCE"` strings and `streamPosition: 0` literals to the `StreamIds`/`EventTypes` constants (positions are now assigned by the stream, matching the persistence-gateway fix from 2026-07-17).
- Fixed an incorrect assertion message in `transcode-variable-encoder.ava.test.js`: the expected error text for an invalid boolean transcode now includes the empty-string case (`possible values [true|false|""]`).
- Minor cleanup in `src/config/constants.js`: removed a stray blank line and added missing semicolons.
- Added `docs/EventSourcing.md`: a walkthrough of the event-sourcing/replay/snapshot mechanism added on 2026-07-17 — what a process instance, flow event, and snapshot are in this project's terms, the real call chain from `POST /start` down to `EventStore.apply`, when automatic snapshots fire, and how `PersistenceGateway.replayStream` rebuilds a read model from a snapshot plus the events after it.
- Implemented process-instance variables end to end, completing a previously half-built skeleton (`Variable`/`VariableEncoder`, and a `saveContext()` stub with a commented-out repository call). Added a new event-sourced `VARIABLE` stream (`variable.orm-model.js`, `VariableRepository.bulkUpsertVariables` via a proper `$set`/`$setOnInsert` bulk write, `VariableProjection`, `PersistenceGateway.saveVariables`, unique-indexed on `(processInstance, name)`, with snapshot/replay support like the other streams). On the codegen side, `workflow.builder.js` now reads `<bpmn:property>` declarations off the BPMN process into typed variable accessors generated in `process-instance-context.js.njk` (one private `Variable` field + getter/setter per declared variable, dirty-checked via `needToSave()`); `service.njk`'s previously-empty `bootstrap(variables)` now assigns incoming values from `POST /start` into the context. Also fixed a bug in `Variable`'s setter: it transcoded the incoming value against the declared type to validate it, then discarded the result and stored the raw untyped value instead. `BaseRepository`/`FakeRepositoryBase` gained a `bulkWrite` passthrough to support this. Verified end-to-end (real BPMN → codegen → generated file inspection, plus persistence/upsert/unique-index/snapshot/replay checks against `mongodb-memory-server`).
- Found (not fixed): `test/resources/andromeda.bpmn` has a pre-existing bug where `<bpmn2:definitions id="andromeda-v9.0">` collides with the child `<bpmn2:process id="andromeda-v9.0">`; bpmn-moddle rejects the process as "unparsable content... duplicate ID" and drops it, so that fixture's main process has never actually been parseable.
- Fixed `POST /start` to accept a plain JSON body, not just `multipart/form-data`: the generated route's `consumes` list (`probe.routes.js.njk`) only allowed multipart, so Fastify rejected JSON requests before they reached the handler; the generated controller now also branches on whether `req.body.variables` arrived as a JSON-encoded string (multipart field) or an already-parsed object (JSON body), instead of always calling `JSON.parse` on it. Both content types use the same `{"variables": {...}}` shape. Verified against a real generated container's actual `route.js`/controller under Fastify: both a multipart and a JSON `POST /start` return 200, and the JSON-supplied variable was confirmed persisted correctly end to end.
- Fixed the actual root cause of variables silently not persisting: generated node methods called `this._context.saveContext()` (async, does real DB writes) without `await` (`build.method.njk`), so a failure bypassed the method's own `try/catch` entirely and became an invisible unhandled promise rejection instead of a logged error. Now awaited. The bootstrap-injected call to the start node (`start.node.processor.js`) is still intentionally fire-and-forget (the `/start` response must return immediately while the workflow runs in the background), but now has `.catch(error => Logger.error(error))` so a failure there is at least logged instead of vanishing. Verified by regenerating a container from scratch and confirming a real `POST /start` with a JSON variable persists correctly. Note: only affects newly compiled containers — existing deployments need recompiling to pick this up.
- Designer: default diagram now declares an `age` (number) process property, matching the `{"age": 20}` default already used in the "Start with Params" popup, so a fresh default diagram exercises the variable feature out of the box.
- Designer: Configuration Settings' "Default Deployment ID" field renamed to "Deployment ID", and it now stays in sync with the diagram's definitions id whenever the properties panel re-derives it (e.g. after an XML edit + Apply), not just when edited directly in that field.
- Fixed the "Start with Params" popup's default content: it had been changed to `{"variables": {"age": 20}}`, but the editor's content *is* the variables object — `DeploymentService.startProcessInstance` already wraps it in a `variables` field before sending, so the double-wrapped default meant the server received `{variables: {age: 20}}`, and since `"variables"` isn't a declared property on the process context, `bootstrap()`'s assignment loop silently skipped it (no error, nothing persisted). Reverted the default to the unwrapped `{"age": 20}` and added an explicit hint in the popup warning against re-wrapping it.
- Verified (no code change): re-ran the full compile → `/start` → persist pipeline using the literal current `EMPTY_BPMN` designer default and bpmn-moddle's own import/export round-trip, to rule out the modeler silently dropping the `<bpmn:property>`/`<bpmn:itemDefinition>` declarations. Both check out — a report of variables still not persisting after all the above fixes is most likely a stale running container process (recompiling alone doesn't restart an already-running embedded container; it keeps executing the code it loaded at startup until stopped and re-run).
- Found and fixed the actual original bug behind variables never persisting via the Designer: `@fastify/multipart` is registered in `web.module.js` without `attachFieldsToBody`, so `req.body` was never populated at all for `multipart/form-data` requests — the controller's `if (req.body && req.body.variables)` check was silently `false` on every multipart `/start` call, which is what both Designer buttons ("▶ Start" and "▶⚙ Start with Params") send. Not something introduced by the earlier fixes; looks like it never worked. Fixed with a route-level `preHandler` on the generated `/start` route (`probe.routes.js.njk`) that manually consumes `request.parts()` for multipart requests, mirroring the working pattern already used by `/api/compile`/`/api/run-embedded` in `engine.routes.js` — deliberately not fixed by enabling `attachFieldsToBody` globally on the shared `web.module.js`, since that file is also used by the root engine and would have broken those two already-working routes (a multipart stream can only be consumed once). JSON requests are unaffected. Verified: regenerated a container, sent the exact multipart request the Designer sends, and confirmed the variable actually reached the database this time — previous verifications only checked the HTTP response succeeded, never that a multipart-sent value was actually persisted.
- Renamed the generated service's `_context` field to `variables`, so script tasks can write `this.variables.age = 23;` directly instead of `this._context.age = 23;` (`service.njk`, `build.method.njk`). `bootstrap()`'s incoming parameter was renamed from `variables` to `incomingVariables` to avoid it being visually confused with the new field name. Verified with a script task literally containing `this.variables.age = 23;`: started with `{"age": 20}`, confirmed the script's write took effect and the persisted value ended up `23`.
- Fixed a pre-existing bug in the generated `/start` OpenAPI spec: `workflow.builder.js` was passing `{responses: {...}, requestBody: {...}}` to `OpenApiGenerator.addResponse()`, which only merges its argument into `.responses` — so the whole thing nested incorrectly (`responses.responses.200` and `responses.requestBody` instead of `responses.200` and a sibling `requestBody`), and `requestBody` never documented `variables` at all, only an unused `deploymentId`. Fixed to call `addResponse`/`setRequestBody` correctly, and now documents `variables` for both `multipart/form-data` (JSON-encoded string field) and `application/json` (object) content types. The request body schema is now generated per-workflow from its actual declared `<bpmn:property>` variables (name, OpenAPI-mapped type, and an example value), via new `mapVariableType`/`buildVariablesSchema` helpers.
- Added manual SQLite support alongside MongoDB, switched via `PERSISTENCE_DRIVER=sqlite|mongodb` (default `mongodb`, no behavior change unless opted in). Uses `sql.js` (WASM SQLite, no native compilation) after `better-sqlite3`'s native addon build failed in this environment (broken Python install, no prebuilt binary fetched). Since sql.js is in-memory, every write exports the whole database back to a shared file and every operation reloads first if the file's mtime is newer than what the process last saw (`SqliteConnection`) — best-effort coordination between the engine and embedded containers pointed at the same file, not real multi-process locking; only the owning engine process (no `deploymentId` env var) resets the file, and only at its own startup (more reliable than resetting on close, which a crash would skip). `embedded.containers.service.js` now passes `PERSISTENCE_DRIVER`/`SQLITE_FILE_PATH` to spawned containers so they share the engine's exact file. New: `table-definitions.js` (schema mirroring all 5 Mongoose models, including the same unique constraints), `sqlite-connection.js`, `sqlite.repository.base.js` (full `BaseRepository`-compatible interface, including `$gte`/sort/upsert/`bulkWrite`), and `repository.factory.js` (replaces the repeated Fake/Mongo branch across all 5 `*Repository` classes — also fixed `ProcessInstanceRepository`/`FlowEventRepository`, which previously had no unit-test-mode branch at all). Verified end-to-end: full process-instance/flow-event/variable lifecycle, snapshot+replay parity, unique-constraint enforcement, an independent `sql.js` load of the file confirming genuine external inspectability, and engine-restart reset. No new failures in the existing MongoDB-path test suite.

## 2026-07-17

- Added event replay and snapshots to the persistence module, making the event store a real source of truth: a new `ReplayService` rebuilds a stream's read model by restoring its latest snapshot (or resetting when none exists) and re-dispatching only the events logged after it, without re-persisting them. Snapshots are read-model state dumps stored in a new `Snapshot` collection keyed by `(streamId, streamPosition)`, written automatically every 100 events (after the event is safely in the log) or on demand. Everything is exposed through `PersistenceGateway.replayStream/replayAll/snapshotStream`, keeping the gateway the persistence layer's only external entry point.
- Engine restarts no longer corrupt event numbering: `PersistenceGateway.init()` now seeds each stream's in-memory position counter from the highest persisted position in the log, instead of restarting at 0 and colliding with the unique `(streamId, streamPosition)` index.
- Fixed status-transition writes (`complete`/`removeLock` on process instances, `close`/`abort`/`fail` on flow events) creating partial, unvalidated documents when the target record didn't exist — they now use a non-upserting update.
- Fixed event `streamPosition` handling: emitted events no longer hardcode position 0 (the stream assigns it), and a legitimate position 0 supplied by a caller is no longer silently overwritten.
- Event timestamps are now ISO-8601 (`toISOString`) instead of locale strings, so they sort correctly and keep millisecond precision.
- Fixed Mongoose `_id` defaults on the process-instance and flow-event models generating the same UUID for every document (`default: v4()` was evaluated once at schema definition).
- Performance: Ajv event and payload schemas are now compiled once and cached instead of recompiled on every event.
- Replaced deprecated Mongoose calls in the base repository (`count`→`countDocuments`, `remove`→`deleteOne`/`deleteMany`), unblocking future Mongoose upgrades.
- Fixed the unit-test fake repository matching a nonexistent `id` field (documents are stored under `_id`) and its `findOne` throwing instead of searching.
