# Changelog

## 2026-07-21

- Fixed multi-workflow containers: previously, compiling two BPMN files into the same container silently broke — the second workflow's generated routes, `WorkflowModel`, and timer service overwrote the first's, since both were written to shared, un-namespaced files/paths (`route.js`, `workflow-model.js`, one `timer.service.js` importing a single hardcoded `{ProcessDef}ProcessInstanceService`). Every workflow's generated files and HTTP routes are now namespaced by its `processDef`: routes are `/{processDef}/start`, `/{processDef}/signal`, and `/{processDef}/tasks` instead of shared `/start`/`/signal`/`/tasks`; each workflow gets its own route file, `{processDef}.workflow-model.js`, and `{processDef}.timer-model.js`. `GET /tasks` is scoped to the calling workflow's own `processDef` (`TaskRepository.findAllActiveTasks`/`PersistenceGateway.findAllActiveTasks` gained an optional `processDef` filter), so two workflows in one container no longer see each other's pending human tasks. Added a new generated service registry (`src/modules/container/registry.js`, rendered once per container from a new `ContainerCodegenContext.registryEntries` list built up as each workflow compiles) mapping every `processDef` to its `ProcessInstanceService` class and `WorkflowModel`, so container-wide code that used to hardcode one workflow can instead resolve the right one at runtime. The timer service (`timer.service.js`) and the timer-catch-resume job were unified to run across all workflows in a container this way: `timer.service.js.njk` now imports every workflow's `TimerModel` and tags each timer with its `processDef`, and the timer-catch-resume job was converted from a per-workflow rendered template (`timer-catch-resume.job.js.njk`) into one static, workflow-agnostic file (`timer-catch-resume.job.js`) that looks up the right service/model via the registry using a `processDef` now threaded through `enqueueCatchResume(...)`. Also added a fail-fast validation (`Utils.prepareContainerContext`) that rejects compiling two BPMN files whose `<bpmn:definitions id="...">` resolve to the same process definition, since that would still collide under the new per-processDef namespacing. Updated ~14 existing integration/unit tests whose hardcoded `/start`, `/signal`, `/tasks` URLs would otherwise have broken under the new namespaced routes, and added `test/integration/two-bpmn-same-container.int.test.js` proving a human-task workflow and a catch-event workflow compiled into the same container run independently (separate routes/tasks, no cross-talk).

- Fixed a regression in the designer's "Start Process Instance" flow (both the Galaxy panel's quick "▶" button and its "▶⚙ Start with Parameters" modal) introduced by the per-`processDef`-namespaced routes above: `DeploymentService.startProcessInstance` was still POSTing straight to a bare `/start`, which every container generated since that change no longer serves (404). Since the designer has no other way to learn a running container's `processDef`(s) from just `deploymentId`+`port`, added a new `GET /api/process-defs` route to generated containers (`probe.routes.js.snjk`, returning `Object.keys(ServiceRegistry)`) — deliberately not folded into the existing `/ready` probe, since `@gquittet/graceful-server` intercepts `/live`/`/ready` at the raw HTTP layer before Fastify's router ever sees them, so a Fastify-level handler on those exact paths is silently unreachable (confirmed live against a real generated container before settling on the new route). `galaxy.controller.js`'s `listContainers` now calls this new endpoint per container and includes `processDefs` in its response (`[]` for containers generated before this existed, or if unreachable). The designer (`GalaxyModal.ts`, `ProcessStartModal.ts`, `DeploymentService.ts`) uses that list: one `processDef` → start directly; zero → fall back to the legacy bare `/start` for old containers; more than one → don't guess, show a picker (`<select>`) in the parameters modal instead. Also, while in this code: fixed `index.html`'s compile button, whose `id`/`title` said "deploy" even though it's wired to `handleDeploy()` (which calls `/api/compile`) and is visibly labeled "Compile" — renamed `id="btn-deploy"` → `id="btn-compile"` with a matching title, updating `main.ts`'s wiring to match.
- Replaced all 15 blocking `alert(...)` calls across the designer (`BPMNDesigner.ts`, `ElementRegistryUI.ts`, `GalaxyModal.ts`) with a new lightweight, self-contained toast notification (`designer/src/designer/Toast.ts` — no new dependency added), styled consistently with the rest of the designer's success/error palette and auto-dismissing after ~4s with a manual close button.

## 2026-07-20

- Implemented Timer Start Event: a `<bpmn:startEvent>` carrying a `<bpmn:timerEventDefinition><bpmn:timeCycle>` (a raw cron expression, e.g. `"0 9 * * *"`) now schedules autonomous process-instance creation via `node-cron`, instead of requiring a `POST /start` call. `start.node.processor.js` detects the timer and validates the cron expression at compile time (via node-cron's own `validate()`, so a bad diagram fails the build, not a running container); the node id/cron are recorded into a new generated `TimerModel` registry (mirrors the existing `WorkflowModel` pattern), which the container's new `timer.service.js` reads at boot to know what to `cron.schedule(...)`.
- Implemented Timer Intermediate Catch Event: a `<bpmn:intermediateCatchEvent>` carrying a `<bpmn:timerEventDefinition>` with either `<bpmn:timeDuration>` (ISO 8601 duration relative to arrival, e.g. `"PT5M"`) or `<bpmn:timeDate>` (an absolute one-off instant) now auto-resumes without a `POST /signal` call. Reuses the existing signal-catch-event two-phase `FlowEvent` pause mechanism as-is; `catch-event.processor.js` computes the due timestamp at arrival time and stores it in the existing `Task.correlation.dueAt` field (no schema change needed). `timer.service.js` runs a 10s node-cron sweep that finds due `Task`s and resumes them the same way a signal would. Added `src/modules/engine/builder/templates/src/utils/iso8601-duration.js` for runtime duration-to-milliseconds parsing in generated containers.
- Added an HA dedupe mechanism so multiple container replicas of the same deployment don't each redundantly fire the same Timer Start Event tick: a new, deliberately non-event-sourced `TimerTick` collection (throwaway idempotency marker, not domain state) with a unique index on `(deploymentId, processDef, nodeId, tickKey)` — every replica racing the same cron fire tries to insert the same document via `PersistenceGateway.claimTimerTick`, and only one insert wins. `tickKey` is the fire time truncated to the whole second (a minute-truncation bug that collapsed every sub-minute cron fire onto one claim key was caught during testing and fixed before landing). Known, accepted limitation: this uniqueness guarantee is only truly atomic under MongoDB — the sqlite driver's (sql.js/WASM) pre-documented best-effort, non-atomic multi-process file coordination means two real sqlite-backed replicas could theoretically both win a claim.
- Added `FlowEventRepository.closeFlowEventIfActive` / `PersistenceGateway.closeFlowEventIfActive`, an atomic status-conditional close (Active → Completed in one operation) replacing the previous separate check-then-close, since a timer-catch sweep and a manual `POST /signal` can now race to resume the same node. `controller.njk`'s `/signal` handler uses this as the final authoritative claim, keeping the existing cheap pre-check only for a fast 404/409 error path. This exposed and fixed a latent bug in `SqliteRepositoryBase.update()`: it re-queried with the same pre-write `cond` after writing, which silently returned `null` whenever the write mutated a field the cond also filtered on (e.g. a status transition) — fixed to capture the row by `_id` first, write, then re-fetch by `_id`, synchronously (no `await` between check and write) so the claim is atomic within a single process too.
- Added dependency `node-cron` (^4.6.0) to both the root `package.json` and the generated container's `package.json.snjk`; new generated-container module `src/modules/engine/builder/templates/src/modules/timer/` (`timer-model.js`, `timer.module.js`, `timer.service.js.njk`), wired into `app.js.snjk`'s boot sequence. Added `test/integration/timer-tick-claim.int.test.js` (a deterministic, single-process proof of the claim primitive, chosen to avoid the sqlite cross-process race flakiness a real two-container test would have), `test/integration/timer-start-event.int.test.js`, and `test/integration/timer-intermediate-catch-event.int.test.js` (covers both `timeDuration` and `timeDate`).
- Added `test/integration/timer-intermediate-catch-event-restore-after-restart.int.test.js` + `test/resources/timer-intermediate-catch-event-restore.bpmn`, the timer-driven counterpart to the existing `intermediate-catch-event-restore-after-restart.int.test.js`: proves a Timer Intermediate Catch Event (an 8s `<bpmn:timeDuration>`) auto-resumes correctly from `timer.service.js`'s own sweep even when the container that paused the instance is stopped and replaced by a brand-new container process that never saw the instance get created, confirming the sweep's `restoreInstance()` fallback is exercised the same way `POST /signal`'s already was.
- Added `test/integration/timer-start-event-two-container-race.int.test.js`, exercising the `TimerTick` HA dedupe mechanism under real two-process contention (complementing `timer-tick-claim.int.test.js`, which proves the claim primitive in-process only, and the single-container `timer-start-event.int.test.js`): runs two embedded container replicas of the same deployment/BPMN (`timer-start-event.bpmn`, cron every 2s) against shared persistence and asserts the completed process-instance count tracks the number of elapsed ticks rather than doubling. Uses tolerant bounds rather than an exact count, since real atomicity for `PersistenceGateway.claimTimerTick` is only guaranteed under MongoDB - this repo's sqlite driver (sql.js/WASM) has pre-existing, documented best-effort, non-atomic multi-process file coordination, an accepted tradeoff for the sqlite dev/test path. Manual re-runs (3x) never showed doubling (5, 5, and 4 completed instances against ~5 elapsed ticks each time). Also noted: EventStore's own sequential `streamPosition` uniqueness constraint acts as an incidental second line of defense on the rare tick where both replicas' local sqlite views race past the TimerTick claim - the observed failure mode was one replica's attempt erroring out (a possible missed tick), never both succeeding (an actual duplicate instance).
- Replaced Timer Intermediate Catch Event's fixed-interval sweep with a real DB-backed job queue: `timer.service.js.njk`'s old `sweepCatchTimers()` (a `cron.schedule('*/10 * * * * *', ...)` full-table scan for due `Task`s) is gone entirely. Instead, `catch-event.processor.js`'s `alternateBody` now calls `TimerService.enqueueCatchResume(nodeId, processInstanceId, dueAt)` the moment a process instance arrives at the node, which schedules a new `TimerCatchResumeJob` (`src/modules/engine/builder/templates/src/modules/timer/timer-catch-resume.job.js.njk`, new generated-container module) via Sidequest (`@sidequest/engine`) for exactly the computed due time (`availableAt`), rather than waiting to be discovered by the next sweep tick. `TimerService.startCatchResumeEngine()` only starts the Sidequest engine at all when the workflow actually has a timer catch event (`jobPollingInterval` 1000ms via `CATCH_JOB_POLLING_INTERVAL_MS`). `workflow.builder.js` gained a `generateTimerCatchResumeJob` codegen step to render this new template into the deployment (initially missing, which surfaced as a `Cannot find module` failure during testing, fixed before landing). Added `test/integration/timer-intermediate-catch-event-jobqueue.int.test.js`, which asserts the same `PT2S`-duration fixture used by the old sweep test now resumes well under the old 10s sweep boundary (asserts under 6s).
- Sidequest runs in-process rather than forked (`fork: false, runner: 'inline'` in `TimerService.startCatchResumeEngine`'s Engine config), since `TimerCatchResumeJob.run()` needs live access to this same process's `ContainerService.processInstances` registry and generated service instances, which a forked child process wouldn't have. `TimerService.resolveBackendConfig()` picks `@sidequest/mongo-backend` (config = the container's existing `MONGODB_URI`) or `@sidequest/sqlite-backend` (config = a dedicated sidequest-specific sqlite file, sibling to but not shared with Andromeda's own sqlite file, since Sidequest manages its own schema/migrations) based on the container's existing `PERSISTENCE_DRIVER`, mirroring the persistence layer's own driver branching. The queue is now pre-declared (`queues: [{name: 'default', concurrency: ...}]`) rather than left to Sidequest's lazy auto-creation on first poll, to sidestep a real bug found in Sidequest 1.16.1 where two replicas racing to auto-create a queue neither has seen yet can both attempt the insert and crash on an unhandled MongoDB duplicate-key error. `manualJobResolution: true` with an explicit `jobsFilePath` (new static template `src/modules/engine/builder/templates/sidequest.jobs.js`, a deployment-root registry of job classes) replaces Sidequest's default stack-trace-based auto-resolution, which doesn't work against this generated container's directory layout. Distributed exactly-once dispatch relies on Sidequest's own backend-level atomic job claim across replicas sharing a backend; `TimerCatchResumeJob` additionally re-checks via the existing atomic `closeFlowEventIfActive` claim, since that's also what keeps a manual `POST /signal` call safe to race against this job for the same node.
- Added dependencies `@sidequest/core`, `@sidequest/engine`, `@sidequest/mongo-backend`, `@sidequest/sqlite-backend`, and `better-sqlite3` (the sqlite backend's native dependency) to both the root `package.json` and the generated container's `package.json.snjk`, plus `"engines": {"node": ">=22.6.0"}` on both, a hard requirement bump - Sidequest itself requires Node >=22.6.0. Fixed a stale bug this exposed: `timer.module.js`'s `start()` called `TimerService.init()` without `await`, harmless while `init()` was synchronous but wrong now that starting the Sidequest engine is a real async operation; fixed to `await TimerService.init()` so `App.init()`'s sequential module startup genuinely waits for the timer engine before starting the web module. Known environment limitation, not a code defect: `better-sqlite3` couldn't be compiled/verified in this sandbox (no working Python for node-gyp - confirmed no `build/` output under `node_modules/better-sqlite3`, and the sandbox's system Node, v20.20.2, is itself below the new >=22.6.0 floor), so only the MongoDB backend path was exercised end-to-end here; the sqlite backend fails fast with a clear "bindings file not found" error rather than hanging.
- Cleaned up the Sidequest migration above (no behavior change): extracted a shared `WorkflowBuilder.renderTemplateToDeployment()` helper for the common "read a template, render via nunjucks, write it into the deployment" pattern, and moved `generateWorkflowContext`, `generateTimerService`, and `generateTimerCatchResumeJob` onto it instead of each keeping its own copy of that logic.
- Fixed doc/test comments left over from the old fixed-interval timer sweep (removed above in favor of `TimerCatchResumeJob`) that still described it as the active mechanism - updated in `persistence-gateway.js`, `flow-event.repository.js`, `controller.njk`, and the timer intermediate catch event integration test headers, which now also clarify that the sqlite-backend path is covered by this suite's default-driver tests while `timer-intermediate-catch-event-jobqueue.int.test.js` covers the MongoDB-only Sidequest path.

## 2026-07-19

- Partially reverted the `Task`-replaces-`FlowEvent` migration from earlier today, per explicit correction: `Task` is meant for external consumers (Galaxy, other APIs) to list/inspect pending work, not to replace the container's own internal pause/resume gating. Restored the `FlowEvent`-based mechanism as the authoritative one: `isTwoPhaseComponent()` and `createFlowEvent()`'s Active/status-0 special-casing (service.njk), and `FlowEventRepository`/`PersistenceGateway`'s `findActiveFlowEvent`/`findAllActiveFlowEvents` (both removed earlier today, now back). `POST /signal` (controller.njk) once again checks/closes the `FlowEvent` to decide whether a resume is legitimate; it *also* still closes the `Task` record afterward (best-effort — a missing/already-closed Task doesn't block a resume FlowEvent already confirmed as legitimate) so the external-facing record's lifecycle stays in sync. `Task` creation itself was never removed — `catch-event.processor.js`/`human-task.node.processor.js` still call `PersistenceGateway.createTask(...)` in `alternateBody` alongside the FlowEvent, and `GET /tasks` still reads from `Task` directly (that endpoint *is* one of the "external APIs" Task exists for). Net effect: both records exist side by side again — FlowEvent gates, Task is for visibility — rather than Task fully subsuming FlowEvent's role. Updated processor doc comments to describe the dual-tracking model accurately. Verified: all three two-phase-node integration tests (`intermediate-catch-event-signal`, `intermediate-catch-event-restore-after-restart`, `human-task`) still pass against the restored mechanism.

- Replaced the ad-hoc `FlowEvent.status=0` overload used to track two-phase (catch event / human task) pause state with a dedicated, event-sourced `Task` collection — a proper source of truth instead of piggybacking on the "was this flow traversed" audit record. New `Task` model (`deploymentId`, `processDef`, `processInstance`, `nodeId`, `nodeName`, `type`: `CatchEvent`|`HumanTask`, `status`: Active|Completed, `correlation`: an untyped JSON object — not queried against yet, but carries whatever a future broadcast-style signal delivery would match a waiting task on, e.g. a catch event's signal name), built through the full event-sourced stack the same way `Variable`/`FlowEvent` already are: `TaskStreamBuilder` (`CREATE_TASK`/`CLOSE_TASK`, both schema-validated), `TaskProjection`, `TaskRepository`, an sqlite table definition, and `PersistenceGateway.createTask`/`closeTask`/`findActiveTask`/`findAllActiveTasks`. `catch-event.processor.js` and `human-task.node.processor.js`'s `alternateBody` (the code that runs when a process instance first arrives and pauses) now calls `PersistenceGateway.createTask(...)` directly — needed a new `processDef` instance field on the generated service class (`service.njk`) so that runtime code has something to read it from, since the processors only produce a body string, not a fresh template render with `{{ ProcessDef }}` available. `controller.njk`'s `/signal` handler now checks/closes the `Task` instead of the `FlowEvent` (still uses `WorkflowModel` for one thing FlowEvent-based tracking never needed replacing: finding the incoming flow's id to populate `flowModel.id`), and `/tasks` reads `findAllActiveTasks('HumanTask')` directly instead of cross-referencing every active flow event against `WorkflowModel` — simpler now that type/name are already on the Task record. Since `Task` is now the sole owner of pause tracking, removed the now-dead `isTwoPhaseComponent()`/`createFlowEvent()` special-casing (service.njk) and the `FlowEventRepository`/`PersistenceGateway` `findActiveFlowEvent`/`findAllActiveFlowEvents` methods added for the prior two-phase turns — leaving them in would have meant an incoming flow into a two-phase node got created Active (0) and then never closed, since nothing calls `closeFlowEvent` for it anymore. Verified: all 8 `test/integration/*.int.test.js` BPMN-driven tests (including both two-phase ones, re-run against the new Task-backed `/signal`/`/tasks`) pass individually with no regressions.

It resumes through the same generic `POST /signal` route from the catch-event work — that handler was already node-type-agnostic (looks a node up purely by id via `WorkflowModel`), so no new route was needed there, just generalized its error messages/docs off "catch event" specifically. Also updated `catch-event.processor.js`'s doc comment, which had gone stale after the restore-after-restart work above — it still described the old in-memory-only limitation as current. Added `GET /tasks` (new `FlowEventRepository.findAllActiveFlowEvents`/`PersistenceGateway.findAllActiveFlowEvents`, cross-referenced against `WorkflowModel` to keep only flows targeting a `UserTask`): without a way to discover what's actually waiting, a caller has no way to get the `processInstanceId`/`nodeId` `/signal` needs in the first place — deliberately excludes pending catch events (a human doesn't "complete" a signal wait). Added `test/integration/human-task.int.test.js` + `test/resources/human-task.bpmn` (Start → script task → human task "Review submission" → End): verifies the pause, that `GET /tasks` lists the exact pending task (id, name), that `POST /signal` with a `variables` payload (simulating form output) completes it and the workflow finishes with that value persisted, and that the completed task no longer appears in `GET /tasks`. All seven `test/integration/*.int.test.js` BPMN-driven tests still pass individually with no regressions.

- Closed the "known limitation" from the intermediate-catch-event work above: `/signal` previously 404'd outright if the paused process instance wasn't currently live in the resuming container process's memory (e.g. the container that paused it had since restarted), since `ContainerService.processInstances` is per-process and starts empty on every restart. Inspired by jsflow's `createInstance(id)` restore path (`restoreProcessInstanceFormPersistentStore`/`getProcessInstanceStatus`/`variables.restoreVariableValues`) — adapted, not ported, since Andromeda tracks two-phase "waiting" state via `FlowEvent` rather than jsflow's dedicated per-gateway status map. Added `{ProcessDef}ProcessInstanceService.restoreInstance(processInstanceId)` (service.njk): looks the instance up via a new `PersistenceGateway.getProcessInstance`/`ProcessInstanceRepository.getProcessInstance`, returns `null` if it doesn't exist or isn't Active (never resurrects a Completed/Aborted instance), otherwise reconstructs it via the constructor's already-existing (but previously never actually exercised) `processInstanceId` resume path, rehydrates its variables via a new `restoreVariableValues()` on the context class (process-instance-context.js.njk; reads every persisted `Variable` row for the instance via a new `PersistenceGateway.getVariables` wrapping the already-existing `VariableRepository.getVariables` and assigns each through the real setter — so it gets transcoded to its declared type exactly like any other assignment — then marks it clean immediately, since it's not a new change), and re-registers it in `ContainerService`'s registry. `controller.njk`'s `/signal` handler now falls back to `restoreInstance()` only when the in-memory lookup misses, so the already-fast common case (instance still live) is unaffected. Added `test/integration/intermediate-catch-event-restore-after-restart.int.test.js` (reuses the fixture from the test above): starts a process instance in one embedded container, lets it pause, stops that container entirely, starts a second, independent container process for the same deployment (sharing the same persisted database, empty in-memory registry), and signals the *second* container — verified via the containers' own logs that two genuinely different PIDs handled the pause and the resume, confirmed the pre-restart variable value survived the round trip, and confirmed the post-signal script task's update landed correctly on top of it.

- Implemented `bpmn:IntermediateCatchEvent` support (pause a process instance until an external signal resumes it), inspired by beeflow's design — though beeflow's own implementation turned out to be an unfinished prototype (the resume path was never actually wired: its generated `/signal` handler creates a brand-new process instance instead of resuming the paused one, and its `resumeExecution`/`executeBody` flags are read but never actually set anywhere), so only its `NodeContext` shape (`executeBody`/`alternateBody`, matching Andromeda's own already-dormant `build.method.njk` scaffolding almost field-for-field) carried over; the actual pause/resume wiring below is new. `CatchEventNodeProcessor` was previously unregistered dead code with the wrong BPMN type (`bpmn:CatchEvent`, an abstract meta-model type bpmn-moddle never actually parses an element as — real catch events parse as `bpmn:IntermediateCatchEvent`) — fixed the type, registered it in `bpmn.processor.js`, and extracts the signal name off `eventDefinitions[0].signalRef.name` when the diagram declares one (not required — a catch event with no event definition still pauses generically). Also fixed `isTwoPhaseComponent()` (service.njk) which checked for the same wrong `"CatchEvent"` string, so a real catch event's incoming flow was never actually being marked Active/pending as intended. On first arrival `flowModel` is the raw incoming-flow-id string used everywhere else in this codebase (see 2026-07-18's parallel-gateway/exclusive-gateway work), so `flowModel.executeBody` is always falsy and the node naturally falls into `alternateBody` (log "now waiting") without reaching its outgoing flows — no special-casing needed there. Added a generic `POST /signal` route (one handler for every catch event node in a workflow, not one route per node): looks the process instance up in `ContainerService`'s existing (already-built, just never used for this) in-memory instance registry, confirms via a new `PersistenceGateway.findActiveFlowEvent`/`FlowEventRepository.findActiveFlowEvent` that it's genuinely still paused at that node (not already resumed or never reached), applies any given `variables`, closes the pending flow event, and calls `fn_<nodeId>({executeBody: true, id: flowId})` directly — deliberately not through `callFunction`, since its `...Object.values(args)` spread only forwards a single positional value and can't carry an `{executeBody, id}` shape. Known limitation (documented in code, not silently swept under the rug): resume only works while the process instance is still live in that container process's memory — there's no rehydration of a paused instance's variables from persistence after a container restart; no code anywhere in the engine has that capability yet. Along the way, found and fixed a real, previously-invisible bug in `web.module.js`'s global Fastify error handler: it unconditionally replied with a bare `500` and an empty body for every thrown error, discarding whatever `.statusCode`/`.message` the route handler had actually set — harmless for `/start` (which never needed to distinguish error cases in its response), but it broke `/signal`'s very reason for setting 400/404/409 (so a caller can tell "you sent garbage" from "already resumed" from "server broke") outright, silently downgrading all of them to opaque 500s. Fixed to respect a valid `error.statusCode` and return `{message}` in the body. Added `test/integration/intermediate-catch-event-signal.int.test.js` + `test/resources/intermediate-catch-event-signal.bpmn` (Start → script task → catch event waiting on signal "approval" → script task → End): verifies the instance genuinely pauses (Active process instance, catch event's outgoing flow never fires, downstream variable still holds its pre-pause value) before signaling, that signaling resumes it to completion with the downstream variable correctly updated, and that a second signal to the same already-resumed node is rejected with 409 rather than silently re-running it.

- Fixed a real crash reported from a live diagram: `VariableEncoder.transcodeVariable`'s `boolean` case only special-cased `value === undefined`, not `value === null` , but `Variable`'s private `#currentValue` field defaults to `null`, not `undefined`. Worker-executed script tasks' `applySnapshot()` re-applies *every* declared variable through its setter after each script task runs, not just the ones that script touched, so any script task that left a declared boolean variable untouched hit this: `this[name] = snapshot[name]` → the setter → `transcodeVariable(null, "boolean", ...)` → thrown `cannot transcode variable X of type boolean, possible values [true|false|""]`, crashing the node's method entirely (matches the reported stack trace, which crashed inside `fn_SetAge`, a script task that only ever touched a different variable). Fixed by treating `null` the same as `undefined` at the top of `transcodeVariable` , pass through unchanged rather than attempting type coercion, for every type, not just boolean (other types didn't throw on `null` but silently produced wrong values, e.g. `string` would stringify it to the literal text `"null"`). Added a `null` case to the existing `transcode-variable-encoder.ava.test.js` boolean suite, plus a new integration-level regression test (`test/integration/transcode-variables-worker.int.test.js` + `test/resources/untouched-boolean-variable.bpmn`) exercising the actual runtime path this bug lives in (worker thread → `applySnapshot` → transcode), not just the unit-level function call: a script task sets `age` only, leaving a declared `isAdult` boolean untouched (must not crash), then a second script task sets `isAdult` from `age` (must correctly transcode `true` through the same worker round trip). Verified the regression test actually catches the bug: reverted the fix and confirmed the test fails (process instance never completes, crashing in `fn_SetAge` exactly as reported) before restoring it.
- Implemented conditional sequence flow and real exclusive (XOR) gateway branching, inspired by andromeda's design: its `ExclusiveGatewayProcessor` is a thin pass-through that doesn't touch conditions at all , the shared next-node dispatch logic evaluates each outgoing flow's own `conditionExpression` independently and only takes flows that evaluate truthy, off of ANY node type, not just gateways. Andromeda already computed this per-flow `executable` flag (`build.method.next.calls.njk`) but never actually gated the call on it , every outgoing flow fired unconditionally regardless.
